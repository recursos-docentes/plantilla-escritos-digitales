Recursos docentes

Cómo armar un escrito digital
paso a paso

De los apuntes de clase a un examen autocorregido, publicado y listo para tomar en la sala de informática.

1Arquitectura del sistema

Antes de tocar nada, conviene entender qué hace cada pieza.

El sistema consta de dos archivos, y cada uno vive en un lugar distinto:

ArchivoDónde viveQué hace
escrito-template.html Publicado como sitio (GitHub Pages u otro hosting) Es el examen en sí: preguntas, pantalla completa forzada, anti-doble-envío. No contiene ninguna respuesta correcta.
Code.gs Pegado en el editor de Apps Script de una Google Sheet Recibe cada intento, corrige y guarda la fila en la planilla. Ahí — y solo ahí — vive la clave de respuestas.

Esa separación es la que impide ver las respuestas correctas incluso abriendo el código fuente del HTML (F12): simplemente no están ahí.

Lo que se va a construir Preguntas armadas a partir de apuntes de clase → pegadas en el HTML → una planilla con Code.gs → la clave de respuestas en Code.gs → todo publicado y probado.

2Descargar la plantilla

Punto de partida: el repositorio con los dos archivos ya armados, listos para adaptar.

  1. Entrar a la página del repositorio: github.com/recursos-docentes/plantilla-escritos-digitales.
  2. Hacer clic en el botón verde Code y elegir Download ZIP.
  3. Descomprimir el archivo descargado en cualquier carpeta.

El contenido incluye:

  • escrito-template.html — el examen, autocontenido (HTML + CSS + JS en un solo archivo)
  • Code.gs — el script de corrección y guardado
  • README.md — la documentación técnica completa, para consultar en caso de necesitar más detalle en algún paso

3Generar las preguntas con IA

No hace falta escribir el array de preguntas a mano.

Las preguntas se pueden armar a partir de un cuaderno de NotebookLM con apuntes de clase ya cargados, o pegando esos apuntes directamente en Gemini. En cualquiera de los dos casos, el mismo prompt le pide a la IA que devuelva el contenido ya en el formato exacto que necesitan el HTML y el Code.gs — alcanza con copiar y pegar, sin retocar la estructura.

Cómo usarlo En NotebookLM: abrir el cuaderno con las fuentes cargadas y pegar el prompt en el chat. En Gemini sin NotebookLM: adjuntar o pegar los apuntes correspondientes en el mismo mensaje, antes del prompt.
prompt para NotebookLM / Gemini
Actuar como asistente para armar un escrito digital de [MATERIA / TEMA], para estudiantes de [GRUPO/CURSO]. Usar únicamente el contenido de las fuentes cargadas (apuntes, guías y ejercicios de clase) — no inventar contenido que no esté en ellas.

Generar [CANTIDAD] preguntas que cubran los temas principales de las fuentes, combinando estos tipos:
- "single": opción única, 4 opciones, una sola correcta
- "tf": verdadero o falso
- "blank": completar código con uno o más espacios en blanco
- "open": pregunta de desarrollo, se corrige a mano, no lleva respuesta correcta

Cada pregunta debe tener exactamente esta estructura (es el formato que se pega en el array "questions" de un archivo HTML):

{
  id: "qN",
  type: "single" | "tf" | "blank" | "open",
  text: "enunciado de la pregunta",
  code: "fragmento de código opcional, con \n para saltos de línea",     // solo si la pregunta muestra código
  options: [ { id: "a", label: "..." }, { id: "b", label: "..." }, { id: "c", label: "..." }, { id: "d", label: "..." } ],  // solo si type es "single"
  blanks: 2   // solo si type es "blank": cantidad de marcadores __BLANK0__, __BLANK1__... usados en "code"
}

Reglas:
- Los id van en orden: q1, q2, q3, etc.
- En las preguntas "blank", el código incluye marcadores __BLANK0__, __BLANK1__, etc., y "blanks" indica cuántos hay.
- En las preguntas "open" no van ni "options" ni respuesta correcta.
- No marcar la opción correcta dentro del "label" que ve el estudiante.

Devolver la respuesta en dos bloques de código separados, sin texto entre ellos:

BLOQUE 1 — array completo, para pegar en escrito-template.html reemplazando "const questions = [...]":
(el array de preguntas)

BLOQUE 2 — para pegar en Code.gs reemplazando las variables HEADERS, QUESTION_IDS y CORRECT_ANSWERS:

var HEADERS = [
  "Timestamp",
  "Nombre",
  "P1 – [resumen breve de la pregunta 1]",
  ... (una entrada por pregunta, en orden, con un resumen corto del enunciado)
  "Autocorrección (X/[cantidad de preguntas autocorregibles, sin contar las 'open'])"
];

var QUESTION_IDS = ["q1", "q2", "q3", ...];

var CORRECT_ANSWERS = {
  // omitir por completo las preguntas "open"
  q2: "b",                 // single → letra de la opción correcta
  q3: "true",              // tf → "true" o "false"
  q4: ["resp1", "resp2"]   // blank → una respuesta por cada blanco, en el mismo orden
};
Revisar antes de pegar La IA a veces se equivoca con una coma de más o de menos, o con el orden de los ids entre el bloque 1 y el bloque 2. Antes de guardar, conviene comprobar que cada id del array de preguntas aparezca una sola vez en QUESTION_IDS y, si corresponde, en CORRECT_ANSWERS.

4Pegar las preguntas en el HTML

Todo pasa dentro de escrito-template.html, en la zona marcada como configuración.

Abrir el archivo con cualquier editor de texto y ubicar const questions = [. Reemplazar todo el contenido del array por el Bloque 1 devuelto por la IA.

Junto a esa misma línea hay otras dos constantes para completar a mano:

ConstanteQué poner
QUIZ_TITLEEl nombre del examen tal como se va a mostrar arriba, por ejemplo "Programación Avanzada — Parcial 1"
LS_KEYUn identificador único para ese escrito puntual, por ejemplo "progavanzada_parcial1_2026"
Por qué importa LS_KEY El sistema anti-doble-envío guarda esa clave en el navegador del estudiante. Si dos escritos distintos publicados en el mismo sitio usan la misma clave, el segundo va a aparecer como "ya enviado" sin haberse hecho. Conviene usar una clave distinta para cada escrito.

5Crear la planilla y pegar el Code.gs

Ahí va a vivir la clave de respuestas, separada del HTML que ve el estudiante.

  1. Crear una Google Sheet nueva y vacía (no hace falta escribir nada en ella todavía — los encabezados los crea el script solo).
  2. Menú Extensiones → Apps Script.
  3. Borrar el contenido de Code.gs que aparece por defecto y pegar el archivo completo de la plantilla.
  4. Reemplazar HEADERS, QUESTION_IDS y CORRECT_ANSWERS por el Bloque 2 devuelto por la IA.
  5. Guardar (Ctrl+S).
Encabezados automáticos No hace falta escribir la fila 1 a mano en la planilla: la primera vez que llega una respuesta (o al correr la prueba manual), el script escribe los encabezados de HEADERS y les da formato solo.

6Publicar como aplicación web

Este paso convierte el script en una URL que el HTML puede llamar.

  1. Implementar → Nueva implementación.
  2. Tipo: Aplicación web.
  3. Ejecutar como: Yo.
  4. Quién tiene acceso: Cualquier persona.
  5. Autorizar cuando lo solicite — el aviso de "app no verificada" es normal, se trata de un script propio.
  6. Copiar la URL que termina en /exec (la de la sección App web, no la de "Biblioteca").
Para actualizar Code.gs más adelante Editar y guardar el script no alcanza para que los cambios se reflejen. Es necesario ir a Implementar → Administrar implementaciones → ✏️ → Nueva versión → Implementar. Crear una implementación nueva desde cero genera una URL distinta; conviene evitarlo salvo que sea necesario.

7Conectar el HTML con la planilla

Un solo dato conecta las dos piezas.

Volver a escrito-template.html, buscar la constante SHEET_WEBAPP_URL y pegar ahí la URL copiada en el paso anterior.

8Publicar y probar el escrito

Último tramo antes de usarlo con estudiantes.

Publicarlo en un sitio es opcional El archivo HTML funciona igual sin subirlo a ningún hosting: alcanza con entregárselo a cada estudiante como un archivo (por ejemplo, adjunto en una tarea de Classroom, por correo o por pendrive) para que lo abra directamente en el navegador. La conexión con la planilla funciona igual en los dos casos, porque no depende de dónde esté alojado el HTML — solo de la URL pegada en SHEET_WEBAPP_URL. Publicarlo en un sitio (GitHub Pages u otro hosting) es más cómodo si se va a reutilizar el mismo escrito varias veces o con varios grupos, porque evita repartir el archivo cada vez.
  1. Renombrar el archivo a index.html si se va a publicar en un sitio (no hace falta si se va a repartir como archivo).
  2. Publicarlo (GitHub Pages es lo más simple) o entregarlo directamente como archivo a los estudiantes.
  3. Abrirlo y completarlo como lo haría un estudiante: revisar que solicite pantalla completa, que las preguntas se vean bien, y que al enviar aparezca la fila correspondiente en la planilla.
  4. Probar también qué ocurre al intentar reabrirlo en el mismo navegador (debería avisar que ya fue enviado).

Una limitación conocida En iOS (Safari y cualquier otro navegador ahí, porque todos usan WebKit) no se puede forzar la pantalla completa. El escrito lo detecta y deja continuar igual, avisando, para no bloquear a esos estudiantes.
